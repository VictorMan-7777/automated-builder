## Rationale

The current issue-resolution constitution references "BOUNDED state" and "Automated Mode" in multiple locations but never formally defines them. This creates ambiguity in enforcement:

1. **BOUNDED state** is invoked in prompts but has no formal definition of what it prohibits or requires
2. **Automated Mode** is referenced in Inventory Verification Stage-2 Dependency Rules but never defined
3. **Terminology inconsistency**: Templates use "BOUNDED mode" (line 18, 152, 214 of issue-resolution-templates.md) while current prompts use "Constraint state: BOUNDED"—neither has a formal definition
4. Mode violations are undetectable because no validation rules exist
5. **HALT behavior undefined**: "HALT on constraint violation" appears in rules but what HALT means is unspecified

This addition provides:
- **Explicit trigger condition**: `"You are in BOUNDED mode. No scope expansion."` (matching templates)
- **Variant recognition**: Acknowledges current prompt phrasing divergence and treats both as valid triggers
- **Enumerated prohibitions**: Clear boundaries for what BOUNDED state prevents
- **Defined enforcement mechanism**: HALT means "stop execution and report the specific violation"
- **Automated Mode definition**: Scoped to inventory verification only, with robust invariant reference
- **Definitional foundation**: Establishes the semantic basis that later enforcement issues (HR-2, HR-5, HR-6) will reference

**Note on Scope**: This issue provides the **definitional foundation** for mode constraints. It does NOT implement execution enforcement for approval transitions or lifecycle sequencing—those are addressed by downstream issues (Issue-005: Approval Transition Mechanics, Issue-006: Approval Lifecycle Execution Contract). Issue-001 establishes WHAT the constraints are; later issues establish HOW they are mechanically enforced.

## Amendment Governance

This section defines how Issue-001 may be amended during the proposal stage (pre-approval) and post-approval, with strict safeguards against scope expansion, recursion, and structural drift.

### A. STRICT Amendment Cascade Rule (Bounded, Non-Recursive)

This rule governs how amendments to Issue-001 are evaluated for derivative issues.

**1. Derivative Issue Identification (Analysis Phase Only)**

For each amendment proposal to Issue-001, evaluate:
- **Ambiguity introduced**: Does the amendment create new undefined terms or unclear boundaries?
- **New enforcement surface**: Does the amendment add new prohibitions or requirements requiring separate enforcement?
- **New dependencies**: Does the amendment create dependencies on other issues or system components?
- **Sequencing implications**: Does the amendment affect the order in which issues must be resolved?
- **Conflicts with resolution order**: Does the amendment create conflicts with the existing dependency chain?

**2. Manual Derivative Issue Creation**

If derivative issues are identified:
- **No automatic issue creation**: Derivative issues are NEVER auto-created
- **Explicit human confirmation required**: Each derivative issue requires human approval before creation
- **Bounded within Issue-001 context**: All derivative issues remain internal to the Issue-001 proposal (using sub-numbering scheme)
- **Each derivative issue must include**:
  - True severity classification (CRITICAL, HIGH, MEDIUM, LOW)
  - Explicit dependency mapping (what it depends on, what depends on it)
  - Singleness validation (confirms issue addresses exactly one defect)

**3. Single Bounded Cascade Pass**

To prevent infinite recursion:
- **Only one cascade evaluation pass per amendment**: Each amendment triggers at most ONE evaluation
- **No recursive cascade triggering**: Derivative issues do NOT auto-trigger further cascades
- **Amendments may NOT auto-generate amendments**: No chaining of amendment actions
- **Further cascade passes require explicit new amendment review**: Human must initiate any subsequent evaluation

**4. Revalidation Triggers (Manual Checklist)**

After creating derivative issues, manually validate:
- **Severity validation**: Each issue classified at correct severity level
- **Dependency validation**: All dependencies explicitly mapped and non-circular
- **Singleness validation**: Each issue addresses exactly one atomic defect
- **Resolution order validation**: Issues can be resolved in dependency order without conflicts

**5. Resolution Order Re-evaluation**

If an amendment alters any of the following, resolution order MUST be explicitly re-evaluated:
- Enforcement hierarchy (what enforces what)
- Guardrails (what prevents invalid actions)
- Preconditions (what must exist before an action)
- Immutability boundaries (what cannot be changed)

When re-evaluating:
- Resolution order changes must be explicitly documented
- Justification for changes must be provided
- No implicit ordering changes allowed

**6. Integrity Constraints**

Amendments MUST NOT:
- Bundle unrelated structural corrections (each defect = one issue)
- Silent severity reclassification (severity changes require justification)
- Create cross-inventory dependencies (Issue-001 stays within P-098)
- Expand scope beyond Issue-001 (MODE CONSTRAINTS definition only)
- Introduce silent structural drift (all changes documented in changelog)

### B. Deferred Derivative Issue Annotation Requirements

When a derivative issue is identified but deferred (not immediately addressed):

**1. Still Created Within Issue-001 Proposal Structure**

Deferred issues are NOT suppressed—they are documented within the proposal.

**2. Required Metadata**

Each deferred derivative issue must include:
- Severity classification (NOT downgraded due to deferral)
- Explicit dependency mapping
- Singleness validation

**3. Required Annotation Block**

```
Status: Deferred
Deferral Justification: <reason for deferring>
Target Resolution Context: <when/where it will be addressed>
Deferral Risk Assessment: <impact of not addressing immediately>
```

**4. Deferral Prohibitions**

Deferral MUST NOT:
- Downgrade severity (deferred CRITICAL remains CRITICAL)
- Remove issue from resolution ordering (still tracked)
- Violate dependency order (dependencies still enforced)
- Bundle atomic defects (singleness still required)
- Suppress structural defects (documented, not hidden)

**5. Dependency Inversion Handling**

If deferral creates dependency inversion (deferred issue blocks non-deferred work):
- Resolution order must be amended explicitly
- Justification must be documented
- Impact on remaining issues must be assessed

**Principle**: Deferral is scheduling, not suppression.

### C. Recursion & Auto-Trigger Safeguards

Explicit prevention of infinite loops and auto-cascading:

**Hard Constraints:**
- ❌ No amendment action auto-creates issues
- ❌ No derivative issue auto-triggers cascade
- ❌ No amendment auto-generates further amendments
- ✅ Only one bounded cascade evaluation pass per amendment
- ✅ Infinite recursion structurally prevented
- ✅ All cascade activity requires explicit human initiation

**Wording Review**: Any proposal language that could be interpreted as auto-triggering MUST be revised to require explicit human action.

### D. Issue Numbering During Proposal Updates (Pre-Approval)

This rule governs how to number issues created during Issue-001's proposal stage (before approval).

**Context**: Issue-001 is currently in proposal stage. All modifications occur within the proposal artifact.

**A. Singleness Splits**

If Issue-001 violates singleness (addresses multiple atomic defects):
- Use suffix letters: **Issue-001a**, **Issue-001b**, etc.
- These represent atomic decomposition of the same root defect
- Each suffix represents one atomic unit of work

**B. Required Satellite Issues**

If new items are required for Issue-001 completion but are NOT singleness splits:
- Use numeric sub-identifiers: **Issue-001-1**, **Issue-001-2**, etc.
- These are dependent satellites within the same bounded proposal
- They support Issue-001 but are distinct work items

**C. Restrictions**

During proposal stage:
- ❌ No new primary issue numbers may be assigned (no Issue-002, Issue-003, etc.)
- ✅ All sub-issues remain internal to Issue-001 proposal
- ❌ Inventory is NOT modified during proposal stage
- ✅ All numbering is local to the proposal artifact

**Rationale**: Inventory is immutable until approved. Proposal-stage decomposition uses sub-numbering to maintain inventory consistency.

### E. Post-Approval Amendment Rule

**After Issue-001 is approved** (proposal renamed to approved, committed):

Any new issue-level change becomes a **formal amendment** and MUST:
1. Receive a new primary Issue number (e.g., Issue-009, Issue-010)
2. Amend the approved P-098 inventory artifact
3. Undergo full evaluation:
   - Severity classification
   - Dependency mapping
   - Singleness validation
   - Resolution order validation
4. Follow formal amendment governance (Amendment Cascade Rule applies)

**Principle**: This preserves inventory immutability. Approved artifacts are permanent records; changes require new formal issues.
